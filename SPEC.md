# ClaudeWatch — Specification (v1)

ClaudeWatch is a Claude Code plugin that enforces Bash command and script
safety via a `PreToolUse` hook. A generic engine evaluates regex rules loaded
from self-contained YAML rule sets and emits a single coalesced decision
(block / ask / allow) for each Bash, Monitor, Write, or Edit invocation. Rules may
target the bash command string or the body of a script file being written or
edited, so destructive intent is caught both inline (`pwsh -Command "..."`)
and at the moment a script file is authored.

This spec captures the contract — what the system must do — independent of
how it's currently implemented. Mechanism notes (current file layout, parser
internals) live in §11.

Requirement IDs use `[XX-NN]`. Categories:

- **EN** — Engine (input, output, lifecycle)
- **RS** — Rule sets (file format, discovery)
- **RL** — Rules (block, ask, except)
- **OUT** — Output decisions
- **LOG** — Decision logging (on by default, opt-out side channel)
- **HK** — Hook wiring
- **EXT** — Extensibility
- **SK** — Skills (`/ClaudeWatch:rules`, `/ClaudeWatch:learn`)
- **DOC** — Documentation
- **DIST** — Distribution / install
- **SH** — Shipped rule sets
- **DEV** — Development workflow

Requirements use [EARS syntax](https://alistairmavin.com/ears) — Ubiquitous (no
keyword), State-Driven (`While`), Event-Driven (`When`), Optional (`Where`),
Unwanted (`If…then`).

---

## 1. Engine (EN)

**Core contract:** Given tool input on stdin, the engine deterministically
emits exactly one of `{deny, ask, no-output}` and exits 0. The engine handles
these tool inputs: `Bash` and `Monitor` (both matched against the shell command
string they carry), `Write` (matched against the new file content), and `Edit`
(matched against the full post-edit file content).

- **[EN-01]** The engine shall read tool input from stdin as a single JSON object.
- **[EN-02]** When `tool_name` is not one of `"Bash"`, `"Monitor"`, `"Write"`, `"Edit"`, the engine shall produce no output and exit 0.
- **[EN-03]** When the relevant input field for the tool is empty or absent, the engine shall produce no output and exit 0. The relevant field is `tool_input.command` for `Bash` and `Monitor`; for `Write` and `Edit` it is `tool_input.file_path` together with the content ([RL-12]), so a `Write` or `Edit` that leaves a file empty is still screened by its path ([RL-21]) and skips only the `file-content` rules.
- **[EN-04]** If stdin is not valid UTF-8, or is not valid JSON (an empty stdin included), then the engine shall emit a `deny` decision with an "unreadable hook input" reason that names the error, and exit 0. Rationale: the host lets a call through when its hook prints nothing, so input the engine cannot read would otherwise reach the host as an allow, including for a command a rule would deny.
- **[EN-04a]** If stdin is not valid JSON, then the engine shall write the parse error to stderr before exiting so the failure is visible in transcripts.
- **[EN-04b]** If the payload is not a JSON object, then the engine shall emit a `deny` decision with an "unreadable hook input" reason naming the payload's type. When `tool_name` is one of the tools in [EN-02], the engine shall likewise deny when `tool_input` is present and not an object, or when a `tool_input` field the engine reads as text (`command`, `content`, `file_path`, `old_string`, `new_string`) is present and not a string; the reason shall name the field and its type. A `null` value reads as absent ([EN-03]). The shape of a payload for any other tool is not read, so [EN-02] holds for it.
- **[EN-05]** The engine shall accept a rules path as its first CLI argument.
- **[EN-05a]** Where the engine is invoked without a rules-path argument, it shall use the directory `../watches` relative to the engine script.
- **[EN-06]** When the rules path is a directory, the engine shall evaluate every `*.yml` file in that directory.
- **[EN-07]** When the rules path is a single file, the engine shall evaluate only that file.
- **[EN-08]** If the rules path does not exist, then the engine shall emit a `deny` decision with a "rules not found" reason that names the path.
- **[EN-09]** When the engine evaluates multiple rule files, it shall process them in a stable, sorted order.
- **[EN-10]** The engine's process exit code shall be `0` regardless of decision or error condition.
- **[EN-10a]** If an exception escapes the engine's decision path, then the engine shall write the traceback to stderr, emit a `deny` decision whose reason names the exception, and exit 0. Rationale: an uncaught exception exits 1, which the host treats as a non-blocking hook error and lets the call through unscreened.
- **[EN-11]** The engine shall not require any third-party Python packages at runtime.
- **[EN-12]** When evaluating a `Write` input, the engine shall match rules against the value of `tool_input.content`.
- **[EN-13]** When evaluating an `Edit` input, the engine shall read the file at `tool_input.file_path`, apply the `old_string` → `new_string` substitution (all occurrences if `tool_input.replace_all` is true, otherwise the first occurrence), and match rules against the resulting full content. The engine shall decode the file by its byte-order mark (UTF-8, UTF-16, or UTF-32) and as UTF-8 when it has none, replacing bytes that do not decode. If the file cannot be read, or `old_string` does not occur in the decoded text, the engine shall match against `tool_input.new_string` alone, so the text an Edit inserts is always screened. Rationale: a file in an encoding the engine does not decode (UTF-16LE without a mark, for one) yields text in which `old_string` never matches, and substituting into it would screen the file unchanged.
- **[EN-14]** When evaluating a `Monitor` input, the engine shall match rules against the value of `tool_input.command` and treat it as a `bash` input throughout — same rule targets ([RL-11]), same command-shape logging ([LOG-03]), same compound-command escalation ([OUT-08]). Rationale: the Monitor tool runs its `command` in the same shell environment as `Bash`, so a Monitor call the engine does not read is an unscreened shell. A Monitor invocation that carries a `ws` object instead of a `command` has no shell command to screen and falls under [EN-03].
- **[EN-15]** Before matching a `bash` input, the engine shall normalize the leading words of each command in it by removing the quoting and backslash escaping that shell syntax permits inside a word, so that `"git" commit`, `g""it commit`, `g\it commit`, `git "commit"` and `rm "-r" /etc` all reach the rules as the shell reads them. A word shall be rewritten only when it resolves to exactly one word whose quoting closes inside it, and only when that word is bare — letters, digits, `_`, `.`, `/`, `-`. A word that resolves to anything else shall be left exactly as written, and the walk shall span at most four words past any prefix it steps over. A leading `VAR=value` assignment or `sudo` prefixes a command without being its program, and an option names one no more than they do, so none of them shall count toward the four; stepping over options is what lets `git -C /repo "push"` and `aws --profile prod "s3" rm` resolve, since both tools carry their global options ahead of the subcommand a rule matches ([SH-01]). Rationale: a rule recognizes a guarded command by the literal text of its program and subcommand, and the shell resolves every one of those spellings to the same word before running anything, so a rule that matches the command as typed must match it as the shell reads it. The bare-word guard is what keeps an *argument* out of it: a quoted operand carrying an operator is data that both the rules and [OUT-08]'s quoted-span handling read as quoted, so unquoting `-m "wip; done"` would turn a commit message into what looks like a command boundary. Normalization is pure string rewriting over the command text, so the decision stays a function of its inputs ([EN-01]). It does not change which text a rule matches *within* a command — patterns search anywhere ([RL-03]), so `echo "rm" -rf /` reaches the same decision as `echo rm -rf /` rather than a different one. This does not close deliberate obfuscation in general — a shell has unbounded ways to spell a word, and variable indirection (`C=git; $C commit`) resolves only at runtime — it closes the spellings that survive as a single literal word.

### Decision logging (LOG)

Logging records each decision for later review (see [SK-13]–[SK-17]) and is on
by default — the decision log is the input the `/ClaudeWatch:learn` workflow
reads. It is separable from the decision: the engine's output is identical
whether or not logging is enabled.

- **[LOG-01]** By default — when `CLAUDEWATCH_LOG` is unset, or set to `1`/`true`/`on`/`yes` (case-insensitive) — the engine shall append one JSON record per evaluated input to the default path `~/.claude/claudewatch/decisions.jsonl`. Where `CLAUDEWATCH_LOG` is set to any other non-disabling value, the engine shall treat it as the destination path and append records there.
- **[LOG-02]** Where `CLAUDEWATCH_LOG` is set to `off`, `0`, `false`, `none`, or the empty string (case-insensitive), the engine shall write no log, and its decision and exit behavior shall be unchanged. This is the opt-out.
- **[LOG-03]** Each log record shall include the decision (`allow`/`ask`/`deny`), the matched rule reasons, a UTC timestamp, and the `session_id`, `cwd`, and active `permission_mode` from the hook input. For a `Bash` or `Monitor` input the record shall include the *command shape* (field `command_shape`) — the program name plus its leading subcommand tokens, with any leading `VAR=value` assignments and `sudo` dropped and the token run stopping at the first flag, path, or value (e.g. `git push --force origin main` → `git push`, `SECRET=… mysql -p… db` → `mysql`) — rather than the raw command string. A command made of several parts (a pipe, a chain, a sequence, a substitution, or a multi-line script) takes the shape of its first part that is not a comment, a `cd`, or a group closer; quoted text, heredoc bodies, and comments never enter a shape. Where rules matched, the record shall also carry `matched_shapes`, a list aligned with the matched reasons giving the shape of the part each rule's pattern matched, or `null` for a reason the engine adds itself ([OUT-08], [OUT-09]), so that a rule firing on `git commit` in `cat msg.txt && git commit -F msg.txt` is filed under `git commit` rather than `cat`. The shapes are what `/ClaudeWatch:learn` groups by ([SK-14]), reading a record without `matched_shapes` by its `command_shape`; recording it rather than the full command keeps inline secrets (credentials in flags, URLs, or assignments) out of the durable, plaintext log. For a `Write`/`Edit` input the record shall include the target file path rather than the file content.
- **[LOG-04]** Logging shall not influence the decision and shall not change the process exit code. If a log write fails, then the engine shall report the failure to stderr and otherwise continue, still emitting its decision.
- **[LOG-05]** The engine shall restrict the decision log to owner-only access — file mode `0600` and its parent directory mode `0700` — applied on each write so a pre-existing wider mode is corrected, so that the plaintext log is not readable by other accounts on the host. A failure to set the mode shall be handled as a log-write failure per [LOG-04].
- **[LOG-06]** The log shall begin with a header line `{"schema": N}` declaring the log's schema version, distinct from the per-input records of [LOG-01]. The current version is `2` (records store the command shape per [LOG-03]); version `1` is the pre-shape format that recorded the raw command string. On write, where the existing log has no header or declares a version other than the current one, the engine shall discard the existing log and start a fresh one with the current header, so that a log written under an earlier schema — which may contain raw commands with inline secrets — is not carried forward across an upgrade. Consumers of the log (the analyzer [SK-13] and the reset tool [SK-19]) shall ignore the header line. The discard applies to the active log only; archived logs ([SK-19]) are user-retained and left untouched.

## 2. Rule Sets (RS)

A rule set is a single YAML file declaring a named bundle of rules.

- **[RS-01]** Each rule set shall declare a top-level `name` field.
- **[RS-02]** Where a `filter` regex is declared, when it does not match the bash command, the engine shall skip all `target: bash` rules in that set. The `filter` shall not gate `target: file-content` rules.
- **[RS-03]** Each rule set shall declare a `rules` map containing optional `block` and `ask` lists.
- **[RS-04]** Where a rule set file is named `*.yml.disabled`, the engine shall not load it.
- **[RS-05]** If a rule set fails to load (parse error, file unreadable), then the engine shall emit a `deny` with a load-error reason and continue evaluating remaining rule sets.
- **[RS-06]** If a rule set's `filter` regex is invalid, then the engine shall emit a `deny` with the regex error and skip the rest of that set.
- **[RS-07]** Each rule set may declare an optional top-level `extensions` field as an inline list (e.g. `extensions: ['.ps1', '.psm1']`). The engine shall evaluate `target: file-content` rules in this set only when the `Write`/`Edit` target file's extension matches one of the listed values (case-insensitive).
- **[RS-08]** If a rule set has no `extensions` field, then the engine shall not evaluate its `target: file-content` rules for any `Write`/`Edit` input.

## 3. Rules (RL)

Rules are the matchable units within a rule set.

- **[RL-01]** Each rule shall declare `name`, `pattern`, and `reason`.
- **[RL-02]** Each rule may declare an optional `ref` URL.
- **[RL-03]** Rule patterns shall be Python regexes matched against the input string with `re.search()` semantics (matches anywhere; no implicit anchoring). The input string depends on the rule's `target`: the bash command for `target: bash`, the script body for `target: file-content`.
- **[RL-04]** If a rule's `pattern` is empty, then the engine shall emit a `deny` with a configuration-error reason naming the rule.
- **[RL-05]** If a rule's `pattern` is an invalid regex, then the engine shall emit a `deny` with the regex error and continue.
- **[RL-06]** Within a rule set, the engine shall evaluate `block` rules before `ask` rules.
- **[RL-07]** Where an `except` regex is declared on an `ask` rule, when both `pattern` and `except` match, the engine shall skip that rule (no ask emitted).
- **[RL-08]** If an `except` field appears on a `block` rule, then the engine shall log a warning to stderr and ignore the field; the block rule shall still fire on `pattern` match.
- **[RL-09]** If a rule's `except` regex is invalid, then the engine shall emit a `deny` with the regex error and continue.
- **[RL-10]** Each rule may declare an optional `target` field with value `bash`, `file-content`, or `file-path`. If omitted, the rule defaults to `target: bash`.
- **[RL-11]** When evaluating a `Bash` or `Monitor` input, the engine shall evaluate only `target: bash` rules.
- **[RL-12]** When evaluating a `Write` or `Edit` input, the engine shall evaluate `target: file-content` rules whose containing rule set's `extensions` list matches the input's file extension, against the content ([EN-03]), and `target: file-path` rules in every rule set, against `tool_input.file_path` ([RL-21]).
- **[RL-13]** If a rule's `target` value is not `bash`, `file-content`, or `file-path`, then the engine shall emit a `deny` with a configuration-error reason naming the rule.
- **[RL-14]** If a YAML line in a rule set does not match any recognized field at its indent level, then the engine shall log a warning to stderr naming the rule set, the rule (when applicable), and the unrecognized line; the engine shall continue processing the remaining lines. This surfaces typos like `refrence:` instead of `ref:` that would otherwise be silently dropped.
- **[RL-15]** An `ask` rule may declare the optional inline-list fields `unless_condition` (named engine predicates) and `unless_regex` (regexes), which exempt the rule the same way `except` ([RL-07]) does. When the rule's `pattern` matches, the engine shall skip the rule (no ask emitted) if **any** `unless_regex` entry matches the input or **any** `unless_condition` predicate matches — OR'd together, and OR'd with `except`. If an `unless_regex` entry is an invalid regex, or an `unless_condition` names a predicate the engine does not ship, the engine shall emit a `deny` with a configuration-error reason naming the rule (an unknown predicate never silently fails to match). Both fields apply only to `ask` rules; on a `block` rule the engine shall log a warning to stderr and ignore them, mirroring [RL-08].
- **[RL-16]** The engine shall ship the `unless_condition` predicate `is_in_project_tree`: it matches (skipping the ask) when the input is a `bash` `rm` command whose every deletion target resolves strictly under an *anchor root*. The anchor roots shall be the working directory (`cwd`) supplied in the hook input and the project root supplied in the `CLAUDE_PROJECT_DIR` environment variable Claude Code exports to hook commands; `/` and the user's home directory shall be rejected as roots, as shall any non-absolute value. A relative target shall be resolved against `cwd` only, since that is the directory the shell itself would resolve it against; an absolute target may sit under either root. `cwd` follows the session's shell and therefore leaves the project the moment the session changes directory into a scratch area, while the project root holds still — anchoring on both keeps an in-repo delete exempt from either vantage point. The check shall be pure string resolution of the command's target paths against the roots — no filesystem access — so the decision stays deterministic; both roots are deterministic per-invocation inputs supplied by the host, so the core contract ([EN] determinism) holds. The predicate shall decline (the ask stands) whenever in-tree-ness cannot be established from the command text: no usable root; the command is compound (handled by [OUT-08]); the program is not `rm`; there are no targets; a target is an anchor root itself or a `.git` directory; a target carries an unresolvable marker (`~`, `$`, backtick, a glob `*`/`?`/`[`, or a `..` segment); or a target resolves outside every root.
- **[RL-17]** The engine shall ship the `unless_condition` predicate `is_ephemeral_scratch`: it matches (skipping the ask) when the input is a `bash` `rm` command whose every deletion target's final path segment names a directory a tool writes and can write again — `.playwright-mcp`, `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`. The premise is the directory's *identity* rather than its location, so unlike [RL-16] the predicate shall ignore where the target sits: deleting one of these loses nothing that re-running the tool does not reproduce, wherever on disk it is. Matching shall be on the final segment only, so a path *inside* such a directory is not exempt and the exemption cannot be widened by appending a subdirectory. The predicate shall decline on the same conditions [RL-16] does for compound commands, parse failures, a non-`rm` program, absent targets, and unresolvable markers, so a glob or variable can never stand in for the name.
- **[RL-18]** The engine shall ship the `unless_condition` predicate `is_recoverable`: it matches (skipping the ask) when the input is a `bash` `rm` command whose every deletion target satisfies [RL-16]'s pure-string under-root resolution **and** is provably restorable from git after the delete: every target is tracked, none is a submodule, and no file under any of them is untracked, ignored, or modified without being committed. A submodule is declined rather than answered for — the superproject records only the commit it points at, so work uncommitted inside it is not visible to the checks made here. Unlike [RL-16] and [RL-17] this predicate reads the filesystem: its checks shall be read-only, shall be bounded by a timeout, and shall fail closed — the predicate declines (the ask stands) whenever a check cannot complete, whether the tool is absent, the timeout elapses, or the command reports failure. This is the sole exemption to the no-filesystem-access property [RL-16] states, and it is scoped to this predicate: the decision stays a pure function of the command, the roots, and the on-disk state those name, with no clock, randomness, or network.
- **[RL-19]** The engine shall ship the `unless_condition` predicate `is_under_scratch_root`: it matches (skipping the ask) when every deletion target of the input sits strictly under a *scratch root*: `/tmp`, `/var/tmp`, `/private/tmp`, `/private/var/tmp`, or `~/.cache`. The `/private` forms are where macOS resolves `/tmp` and `/var/tmp` to, and tools that resolve paths write them that way (Claude Code's session scratchpad sits under `/private/tmp`). The deletion targets shall be the operands of a `bash` `rm` command, or of a `Remove-Item` that makes up the whole script of a `pwsh` or `powershell` invocation, read with the same operand parsing [RL-16] uses; a `Remove-Item` operand shall be split on commas, since PowerShell reads `a,b` as two paths. Each target shall be tested on its own, so one scratch target never exempts another target beside it. The predicate shall decline (the ask stands) on the conditions [RL-16] declines on for a compound command, a parse failure, a different program, and absent targets, and whenever the part of a target past its scratch root is empty, resolves to the root itself, or carries one of [RL-16]'s unresolvable markers (`~`, `$`, backtick, a glob `*`/`?`/`[`, or a `..` segment), so `/tmp/../Users/foo` and `/tmp/$(whoami)` are not scratch. The `~` of `~/.cache` shall be read as text rather than expanded, so the check stays pure string analysis with no filesystem or environment access.
- **[RL-20]** The engine shall ship the `unless_condition` predicate `is_in_tree_or_scratch`: it matches (skipping the ask) when the input is a `bash` `rm` command each of whose deletion targets qualifies on its own under [RL-16] (resolves strictly under an anchor root), [RL-17] (names a regenerable tool directory), or [RL-19] (sits under a scratch root). Rationale: each of those predicates requires every target to qualify on its own terms, so naming them side by side in `unless_condition` ([RL-15]) prompts on a mixed set whose every target is safe (`rm -rf /work/repo/bin /tmp/build`). Deciding per target exempts that set without letting a safe target vouch for an unsafe one. The predicate shall decline whenever any target qualifies under none of the three, and on the command-level conditions the three share (compound command, parse failure, a program other than `rm`, absent targets).
- **[RL-21]** A `target: file-path` rule shall match its `pattern` against the `Write` or `Edit` target path as the tool gives it, ungated by the rule set's `filter` and `extensions`. Rationale: some files are guarded for where they are, whatever is written into them: ClaudeWatch's own overrides ([SH-01] `watch-self`) can be emptied by a `Write` whose content no rule would match.

## 4. Output Decisions (OUT)

The engine emits at most one decision per invocation.

- **[OUT-01]** When emitting a decision, the engine shall write a single JSON object to stdout matching the Claude Code `hookSpecificOutput` schema with `hookEventName: "PreToolUse"` and `permissionDecision` set to `"deny"` or `"ask"`.
- **[OUT-02]** The engine shall format each violation canonically as `<rule-name>: <reason>` (just `<reason>` when the rule has no name), with ` — <ref>` appended when `ref` is present. The rule-set name is omitted — the `ref` link supplies that context. This canonical form is what both the displayed reason and the decision log (`[LOG-03]`) carry.
- **[OUT-03]** When any block rule matches in any rule set, the engine shall emit a single `deny` decision aggregating all block reasons, separated by newlines.
- **[OUT-04]** When no block rule matches and at least one ask rule matches in any rule set, the engine shall emit a single `ask` decision aggregating all ask reasons, separated by newlines — subject to the compound-command escalation in [OUT-08] and the unattended escalation in [OUT-09]. The decision shall be a function of the command alone: the same input grades the same way whatever `permission_mode` the host reports, and the engine shall not read that field on the decision path ([LOG-03] logs it; nothing consumes it). **Whether an emitted `ask` reaches a person is the host's half of the contract and is not guaranteed.** Three behaviors are established: an interactive session in `auto` clears the call before the hook's `ask` has a prompt surface, so the command runs unconfirmed ([claude-code#89561](https://github.com/anthropics/claude-code/issues/89561)), except that as of Claude Code 2.1.319, with telemetry or feature flags off (including behind LLM gateways), calls the auto-mode server can't check are asked about or denied, with no fallback to the built-in classifier unless `CLAUDE_CODE_AUTO_MODE_SERVER=0` is set (per the 2.1.319 changelog; not probed here); a session with `permissions.denyInsteadOfPrompting` on denies any call that would wait on a prompt and continues the turn, in every mode and in subagents and teammates (added in Claude Code 2.1.319); a headless `--print` session has nobody to answer, so the call fails closed and is denied in every mode the probe graded, `auto` included (`tests/probe-host-ask-behavior.sh` on Claude Code 2.1.285; the hook never graded `plan`). The engine cannot distinguish these — `permission_mode` reads `auto` in both the prompted and the prompt-suppressed case, and neither `--permission-prompts none` nor `denyInsteadOfPrompting` sets a field of its own. `auto` is also the host's default: as of Claude Code 2.1.284 an interactive terminal or VS Code session with no permission mode configured starts in `auto` unless `permissions.defaultMode` overrides it ([which mode a session starts in](https://code.claude.com/docs/en/permission-modes#which-mode-a-session-starts-in)). An `ask` is therefore a *request* for confirmation, never evidence one happened, and a rule guarding something unrecoverable belongs in the block tier rather than relying on the prompt.
- **[OUT-05]** When no rule matches, the engine shall produce no stdout output (allow-by-default).
- **[OUT-06]** *(retired in 0.18.0)* — ~~the ask prompt rendered the `<reason>` prose as an OSC 8 terminal hyperlink to the `ref`, with `CLAUDEWATCH_HYPERLINKS` as the opt-out.~~ Claude Code 2.1.235 began sanitizing hook-supplied reason strings, replacing every control character with U+FFFD, so the escape reached the user as visible garbage instead of a link. Both paths now use the canonical ` — <ref>` form of `[OUT-02]`, and `CLAUDEWATCH_HYPERLINKS` is gone.
- **[OUT-07]** A **deny** decision's `permissionDecisionReason` shall end with the ` [plugin:ClaudeWatch]` source tag — but the logged reasons (`[LOG-03]`) shall not. Claude Code annotates ask prompts with the originating plugin but leaves deny errors unattributed, so the engine appends the tag itself on the deny path to keep the source visible. Ask decisions shall not carry the tag (the host supplies it).
- **[OUT-08]** When the coalesced decision for a `Bash` or `Monitor` input is `ask` and the command is *compound* — outside any single- or double-quoted span it contains a shell control operator (`|`, `;`, newline, `&&`, `$(`, or backtick), separates two commands with a lone `&`, or opens a subshell or process substitution — a `(` at command position: the start of the command, after a separator or a redirection, and behind the `time` and `!` keywords — the engine shall escalate the decision to `deny` and prepend a note stating the ask was escalated because a compound command or subshell can be auto-approved segment-by-segment by the host allow list (skipping the confirmation) and that the guarded command should be run on its own to be prompted. Command substitution (`$(`, or a backtick not escaped by a backslash) shall count inside a double-quoted span as well, since the shell runs it there; only a single-quoted span makes it data, so `rm -rf "$(mktemp -d)"` is compound on the same terms as `rm -rf $(mktemp -d)`. Rationale: a `deny` is honored in every permission mode and an `ask` is not ([OUT-04]), so escalating is what keeps a guarded compound from running unremarked. A compound command is the shape where this costs most: the host's allow list can approve a pipeline segment-by-segment and auto-run it before any prompt surfaces, so even a mode that would prompt on the bare command may not prompt on the chained one. The escalation is therefore narrower than the exposure — a bare `ask` is bypassed in `auto` too ([OUT-04]) and is *not* escalated, because escalating every `ask` under a prompt-less mode would hard-block the ordinary workflow (`git commit` and `git push` are the two most frequent ask-tier matches) and the engine cannot tell a prompt-less session from a prompting one anyway. That holds with `auto` as the unconfigured default ([OUT-04]); instead, the ambient guidance ([HK-04]) has the agent point a user who expects prompts at `permissions.defaultMode` (issue #37). The escalation applies only to an `ask` decision (a `deny` already survives, and `allow`/no-match stays silent per [OUT-05]) and only to shell-command inputs — `Bash` and `Monitor` ([EN-14]); `Write`/`Edit` are single operations, not shell pipelines. A `Monitor` command runs unattended and repeats on one approval, so an ask-tier command inside one escalates on the same terms; the way to be prompted is the same, run the guarded command as its own `Bash` call. Every other operator inside a quoted span is string data, not a command boundary, and shall not trigger escalation. A bare subshell groups rather than separates, so it carries none of the listed operators, yet the host treats it as the same class — Claude Code 2.1.257 fixed a `permissions.ask` rule being skipped in auto mode for a command running "inside a compound command or subshell". Restricting the `(` to command position leaves a parenthesis inside an argument alone, since only a leading `(` opens a subshell; `time` and `!` are named because they are the two words that may precede one with no operator between them, and `<`/`>` because a process substitution runs its own command the same way. A lone `&` both backgrounds a command and separates it from the next, so it counts only when something follows it — a trailing `&` is one command — and only away from the redirections it shares a character with (`2>&1`, `>&2`, `&>log`).
- **[OUT-09]** When the coalesced decision is `ask` (after [OUT-08]) and the hook input's `session_id` names a session marked unattended ([SK-20]), the engine shall escalate the decision to `deny` and prepend a note stating that nobody is present to answer the ask and that the step should be left prepared for the user to run on return — unless the input is a `Bash` command on the unattended allowance of [SK-24], in which case the engine shall produce no decision and shall record the allowance per [SK-24]. A session is marked unattended when a file named for its `session_id` exists in `~/.claude/claudewatch/unattended/`; a `session_id` that is absent or not made only of letters, digits, `_` and `-` shall count as not marked. The check is an existence test with no other filesystem access. Rationale: a person who has stepped away cannot answer an `ask`, and in `auto` the `ask` would otherwise run unconfirmed ([OUT-04]) without ever reaching the `PermissionRequest` hook of [HK-06], so the escalation is what keeps the ask tier meaningful while nobody is watching. It applies to every tool the engine screens, since a `Write` or `Edit` the rules ask about is no more answerable than a command.

## 5. Hook Wiring (HK)

- **[HK-01]** The plugin shall register `PreToolUse` hooks that invoke the engine against the plugin's `watches/` directory for the `Bash`, `Monitor`, `Write`, and `Edit` tools. Matchers may be combined via regex alternation (e.g. `matcher: "Write|Edit"`).
- **[HK-02]** *(retired in 0.18.0)* — ~~the plugin shall register a `SessionStart` hook for plugin-update self-checks.~~ Never implemented; the placeholder hook was removed with it. The ambient-guidance `SessionStart` hook of [HK-04] is unaffected.
- **[HK-03]** The plugin shall declare its hooks in `hooks/hooks.json`.
- **[HK-04]** The plugin shall register a `SessionStart` hook that emits ambient guidance into the session context advising that a consequential command be run as its own Bash call rather than piped or chained, so the compound-command escalation ([OUT-08]) is avoided before it triggers. The guidance shall be sourced from `rules/*.md` so it can be edited without changing the hook.
- **[HK-05]** The `PreToolUse` hooks of [HK-01] shall fail closed for every fault the engine process observes: unreadable input ([EN-04], [EN-04b]), a missing rules path ([EN-08]), a rule set that fails to load ([RS-05]), and an exception on the decision path ([EN-10a]) shall each reach the host as a `deny` with exit 0, never as a silent exit or a non-zero one. For the faults the process cannot observe (the interpreter is missing, the process crashes or is killed, the hook times out), each guard hook shall declare `onFailure: block`, so Claude Code blocks the call rather than running it unscreened.
- **[HK-06]** The plugin shall register `UserPromptSubmit`, `PostToolUse` (matcher `Skill`), `PermissionRequest`, and `PreToolUse` (matcher `AskUserQuestion`) hooks that run `scripts/unattended.py`, which maintains the unattended marker of [OUT-09] and acts on it per [SK-20]–[SK-25]. The `PermissionRequest` and `AskUserQuestion` hooks shall declare `onFailure: block`, so a hook that cannot run (the interpreter is missing, the process crashes, the hook times out) denies the prompt or question rather than leaving it to wait on nobody; this holds in attended sessions too, where a broken hook denies what would have been shown. The `UserPromptSubmit` and `PostToolUse` hooks shall not block on failure, since blocking there would refuse the user's own prompt or a completed tool call.

## 6. Extensibility (EXT)

- **[EXT-01]** Where a new `*.yml` file is added to the `watches/` directory, the engine shall auto-discover it on the next invocation without any configuration change to `hooks.json`.
- **[EXT-02]** Where a rule set is renamed from `*.yml` to `*.yml.disabled`, the engine shall stop loading it on the next invocation.
- **[EXT-03]** New rule sets shall not require code changes to the engine.

### Rule overrides (OVR)

A user changes how the shipped rules apply without editing them, so the change
survives a plugin upgrade, which replaces the install folder and everything in
it. An override can move a rule between tiers or turn rules off; it cannot add
a rule, a pattern, or an exemption.

- **[OVR-01]** The engine shall read rule overrides from `~/.claude/claudewatch/overrides.yml`, outside the plugin's install folder. An absent file means no overrides.
- **[OVR-02]** Each top-level key of the overrides file shall name a shipped rule set. Its value is either `off`, which turns the whole set off, or a nested mapping of `<rule name>: <tier>`, where the rule name is the rule's `name` field (optionally quoted) and the tier is `ask`, `block`, or `off`.
- **[OVR-03]** A rule overridden to `ask` or `block` shall be evaluated in that tier with its pattern, target, reason, `ref`, and exemptions (`except`, `unless_condition`, `unless_regex`) unchanged, so a rule moved from ask to block blocks what it used to ask about and still exempts what it used to exempt. A rule overridden to `off`, and every rule of a set overridden to `off`, shall not be evaluated.
- **[OVR-04]** An override naming a rule set or a rule the shipped rules do not contain is *stale*. The engine shall ignore it, and the session-start record ([OVR-06]) shall report it.
- **[OVR-05]** If the overrides file cannot be read or parsed (a line that is neither a set nor a rule entry, a tier other than `ask`/`block`/`off`, a set value other than `off`), then the engine shall emit a `deny` for every screened call, naming the file and the error, as it does for a rule set that fails to load ([RS-05]).
- **[OVR-06]** The plugin shall register a `SessionStart` hook that, where the effective rules differ from the shipped ones, appends a record to the decision log ([LOG-01]) carrying `event: "session_start"`, the session id, the plugin version, each rule whose tier differs (rule set, rule, shipped tier, effective tier), each rule set turned off, and each stale override. It shall write nothing when nothing differs or logging is off. Where the overrides file is malformed or holds a stale override, the hook shall also say so in the session context. A reader of the decision log shall skip records that carry no `decision`.
- **[OVR-07]** `scripts/overrides.py` shall be the one writer of the overrides file: `set` records a tier for a rule or `off` for a set after checking that the shipped rules contain it, removing the entry when the tier equals the shipped one; `reset` removes entries; `show` reports each shipped rule's shipped and effective tier. It shall never edit `watches/`.

## 7. Skills (SK)

The plugin ships interactive Claude Code skills that surface and edit rules
without leaving the session.

### `/ClaudeWatch:rules`

- **[SK-02]** Where the user invokes `/ClaudeWatch:rules`, the skill shall list every shipped rule set with two tables (block, ask) of its *effective* rules ([OVR-03]), using stable IDs of the form `<short-name>-block-NN` and `<short-name>-ask-NN` (zero-padded) assigned in shipped order, and shall mark each rule whose tier an override changed and each rule an override turned off.
- **[SK-03]** When listing rule sets, the skill shall also list any rule set an override turned off, and any stale override ([OVR-04]).
- **[SK-04]** Where the user passes `--list`, the skill shall list rules and exit without entering the edit loop.
- **[SK-05]** When the user enters an edit command, the skill shall accept one operation per turn and loop until the user enters `done`. The supported operations are: `<id>:block` (move the rule to block), `<id>:ask` (move it to ask), `<id>:off` (turn the rule off), `<id>:reset` (restore its shipped tier), `off <name>` (turn a rule set off), `on <name>` (restore a rule set), and `reset` (remove every override). The skill shall not add rules or rule sets.
- **[SK-06]** *(retired)* — ~~scan for duplicate, shadowing, and cross-section patterns before writing.~~ Overrides move or drop shipped rules and cannot add a pattern, so there is nothing new to conflict.
- **[SK-07]** Before writing, the skill shall present a preview of the affected rule tables with each change marked, and shall require explicit confirmation (`yes` / `edit` / `abort`) from the user.
- **[SK-08]** When applying edits, the skill shall write only the overrides file, through `scripts/overrides.py` ([OVR-07]), and shall never edit the shipped rule sets in `watches/`. The skill shall run only edits that move a rule to `block`; for an edit that moves a rule to `ask` or `off`, turns a set off, or resets, which `watch-self` blocks the agent from running ([SH-01]), it shall print the exact commands and ask the user to run them, typed with a `!` prefix (which Claude Code runs without PreToolUse hooks) or in a separate terminal.
- **[SK-09]** When the user issues `off <name>`, the skill shall record `off` for that rule set in the overrides file.
- **[SK-10]** When the user issues `on <name>`, the skill shall remove that rule set's override, restoring its shipped rules.
- **[SK-11]** *(retired)* — ~~`new` created a rule set.~~ Overrides cannot add rules; a new rule set belongs in the plugin's source.
- **[SK-12]** After applying changes, the skill shall load the overrides file the way the engine does and report any error, since a malformed file denies every screened call ([OVR-05]).

### `/ClaudeWatch:learn`

The learn skill aggregates the decision log ([LOG-01]–[LOG-04]) into a batch
of proposed overrides ([OVR-02]), so the user tunes the ask and block tiers from
accumulated history rather than per command. ClaudeWatch's decisions only add
scrutiny ([OUT-01], [OUT-05]), so the skill proposes no host allow rules.

- **[SK-13]** Where the user invokes `/ClaudeWatch:learn`, the skill shall analyze the decision log and present its proposals. If no log exists, the skill shall make no changes and shall report why: when logging is disabled (`CLAUDEWATCH_LOG` set to an opt-out value per [LOG-02]) it shall warn that disabling logging disables `/ClaudeWatch:learn` and explain how to re-enable; otherwise (logging on by default, but no records yet) it shall explain that no sessions have run with the hook active.
- **[SK-14]** The skill shall present two groups: **ask candidates** (commands ClaudeWatch repeatedly asks about, with the matched rule), each with the overrides it could take (`block` to stop asking and refuse, `off` to stop asking), and a **deny summary** (blocked commands grouped by reason), each with the overrides it could take (`ask`, `off`). Records the engine allowed shall inform only the window ([SK-18]) and the permission-mode tally, never a proposal.
- **[SK-15]** The skill shall accept an optional time window (e.g. `--since 1d`) and forward it to the analysis.
- **[SK-16]** Before writing any change, the skill shall present the exact edits and require explicit confirmation, and shall apply only the items the user approves.
- **[SK-17]** The skill shall apply each approved override through `scripts/overrides.py` ([OVR-07]), running a move to `block` itself and handing a move to `ask` or `off` to the user as [SK-08] describes, shall not write to any `settings.json`, and shall change a deny-summary rule only when the user approves that item.
- **[SK-18]** The analysis shall report the window its proposals are drawn from: the number of decision records considered, the count of distinct sessions among them, and the time span from the oldest to the newest record. The skill shall surface this so the user can weigh how much history backs the suggestions.
- **[SK-19]** The skill shall offer to reset the decision log after the user has applied their chosen changes, so that the next analysis measures from the post-change baseline rather than re-surfacing commands the user already decided on. Reset shall **archive** the current log by default — moving it to a fixed user directory (`~/.claude/claudewatch/archive/`, beside the durable log per [LOG-01]) so the prior history is recoverable — and shall support a `--hard` mode that deletes it outright. Where logging is disabled ([LOG-02]) or no log exists, reset shall make no change and shall report why. Reset shall report what it cleared (record count and span).

### `/ClaudeWatch:unattended`

The unattended skill tells the agent how to work while the user is away
(decide, log the decision, keep going), and marks the session so that neither
ClaudeWatch's `ask` nor a host permission prompt waits on a person who is not
there.

- **[SK-20]** When a user prompt's first line begins with `/ClaudeWatch:unattended` or `/unattended`, or when the agent invokes the skill through the `Skill` tool, the session shall be marked unattended by writing the marker file of [OUT-09].
- **[SK-21]** When the user submits any other prompt while the session is marked, the marker shall be removed and a line added to the agent's context saying permission prompts reach the user again. A prompt the harness injects (a background task notification, a system reminder, a message from another session) shall leave the marker as it is, since nobody typed it.
- **[SK-22]** While the session is marked, a `PermissionRequest` for a call outside the unattended allowance ([SK-24]) shall be denied with a message naming the call's shape (the tool, plus the program and subcommand for `Bash`) and directing the agent to take another route or leave the step prepared. Each denial shall be appended as a `DENY` line to a per-session log beside the marker, recording the timestamp and the shape only, never the command's arguments.
- **[SK-24]** The *unattended allowance* is the set of local, recoverable git operations an unattended run needs to segment its work into commits: `git add`, `git commit` without `--amend`, `git switch` without `-f`, `--force`, or `--discard-changes`, and `git checkout -b`, each optionally preceded by `git -C <path>`. A command is on the allowance only when the whole command is one of these forms and is not compound ([OUT-08]). The allowance applies only while the session is marked: the engine stays silent on such a command instead of escalating its `ask` ([OUT-09]), and the `PermissionRequest` hook approves the host's prompt for it instead of denying it ([SK-22]). Every use of the allowance shall be recorded loudly: an `ALLOW` line naming the operation in the per-session log of [SK-22], and, where decision logging is on, an `unattended_allow` field naming it on the decision record ([LOG-03]). The set is defined once, in `scripts/watchdog.py`, and both the engine and the hook read it from there.
- **[SK-25]** While the session is marked, an `AskUserQuestion` call shall be denied before it is shown, with a message telling the agent that nobody is present to answer and to make the call, record it in its notes, and continue. Each denial shall be appended as a `DENY` line to the per-session log of [SK-22].
- **[SK-23]** `scripts/unattended.py on|off|status` shall set, clear, or report the marker for the session named by `CLAUDE_CODE_SESSION_ID`, and `status` shall report the number of calls denied and the number allowed under [SK-24]. An unset or malformed session id shall exit non-zero with a message.

## 10. Shipped Rule Sets (SH)

These are the rule sets the plugin ships out of the box. Each is
self-contained and removable by renaming its file to `*.yml.disabled`.

- **[SH-01]** The plugin shall ship the following rule sets:

  - **`watch-aws`** — AWS CLI operations classified by reversibility. **Block** rules shall cover irreversible operations: AWS operations whose verb begins with `delete-`, `remove-`, `deregister-`, `terminate-`, `purge-`, `reset-`, or `revoke-`; the EC2 `release-address` operation; and the `s3` high-level `rm` and `rb` subcommands. A single **ask** rule shall match any other `aws <service> <operation>`, with an `except` that allows read-only operations (`get-`/`list-`/`describe-`/`head-` verb prefixes and the `s3` high-level `ls` subcommand). Rules shall match through interspersed global flags (`-`-prefixed options before the service and between service and operation), including quoted values containing spaces, so that `aws --profile prod ec2 terminate-instances` is not silently bypassed.

  - **`watch-bash`** — destructive shell primitives in `.sh`/`.bash`/`.zsh` file content authored via `Write`/`Edit`. File-content only; bash-target coverage for the same primitives lives in `watch-files`. **Block** rules shall cover: `rm -rf /` (the trailing `/*` included), `curl|sh`/`wget|sh`, `dd of=/dev/sd*` (and `nvme`/`disk`/`hd`/`xvd`), `mkfs /dev/...`, and `shred`. **Ask** rules shall cover: recursive `rm -rf` (with `except` for `~/.cache/`, `/tmp/`, `/var/tmp/`, `$TMPDIR`), `chmod 777`, recursive `chown -R`, and shell `eval` of dynamic strings. The `rm` rules shall bound `rm` with the same boundaries `watch-files` uses below, the quoted `-c` or `eval` script included, so a script carrying `bash -c "rm -rf /"` is matched. The scratch exemption stays an `except` regex here rather than [RL-19]'s predicate, because an `unless_condition` predicate reads a single `bash` command ([RL-15]) and a script body holds many. That `except` is matched against the whole body, so one scratch delete anywhere in a script exempts every other recursive delete in it.

  - **`watch-dotnet`** — .NET decompilation and NuGet introspection. **Ask** rules nudge agents toward SourceLink rather than decompilation: .NET decompiler invocations (`ilspycmd`, `ildasm`, `dotpeek`, `dnspy`/`dnspyex`, `justdecompile`), `unzip`/`tar` of a `.nupkg` file, `curl`/`wget` of a `.nupkg` URL, and `nuget install`. Decompiler-name matching shall be case-insensitive so that Windows-style executables (`dnSpy.exe`, `ILDASM.exe`) are not bypassed. Each rule's `ref` shall point to SourceLink documentation.

  - **`watch-exec`** — running code that can't be read before it runs. **Block** rules shall cover: a download from `curl` or `wget` run through a `$(…)` or `<(…)` substitution; a download piped to an interpreter other than `sh`/`bash`/`zsh` (those are `watch-installs`' `curl … | sh`), including `dash`, `ksh`, `fish`, `python`, `perl`, `ruby`, `node`, `php`, and PowerShell; a `base64` or `xxd -r` decode piped to a shell or interpreter; and a shell attached to a network connection (`nc`/`ncat`/`netcat` with `-e` or `-c` or piped to a shell, `socat … system:` or an `exec:` naming a shell or interpreter, and `/dev/tcp/` or `/dev/udp/`). An interpreter given an option that supplies its own code (`-m`, `-c`, `-e`, `-p`, `-r`) reads the piped input as data, so `curl … | python3 -m json.tool` is not matched.

  - **`watch-files`** — generic destructive filesystem operations. **Block** rules shall cover: `rm -rf /` (the trailing `/*` included), `chmod 777`, `mv … /dev/null`, `shred`, and writes to a raw disk: `dd of=/dev/…` and `mkfs … /dev/…`, a `>` redirect onto a disk device (`sd`, `nvme`, `disk`/`rdisk`, `hd`, `xvd`, `vd`, `mmcblk`), and `diskutil` erase and repartition verbs. **Ask** rules shall cover: recursive `rm -rf`, recursive `rm -r`, `mv` from a root-level path, `chmod`, and `chown`. A root-level path is `/` itself or a path under a top-level system directory (`/etc`, `/usr`, `/bin`, `/sbin`, `/lib`, `/opt`, `/var`, `/dev`, `/root`, and the like, macOS's `/System`, `/Library`, `/Applications`, and `/private/etc` and `/private/var` included); home directories and the temp directories (`/tmp`, `/private/tmp`, `/var/tmp`, `/var/folders`) are not. The two recursive-rm ask rules shall carry the `unless_condition` `is_in_tree_or_scratch` ([RL-20]), so a recursive delete is allowed when each of its targets is confined to the working tree (recoverable from git history), names a regenerable tool directory wherever it sits, or sits under a scratch root, while a delete with any target reaching elsewhere still asks. The predicate reads only a bare `rm`, so an `rm` inside a `-c` or `eval` script asks whatever its target. The `rm` rules shall read recursive and force as independent options, so that every spelling of the pair matches — clustered (`-rf`), split (`-r -f`), reordered, long (`--recursive --force`) along with every prefix GNU `rm` accepts for them (`--rec`, `--f`), and the `-R` synonym — and shall bound `rm` with shell-command boundaries rather than `\b` (as the `watch-secrets` entry below requires for the same reason), so `my-rm` does not match. A quote shall also count as a boundary where it opens a script the shell runs: after `eval`, or after the `-c` option of a shell invocation (`sh`, `bash`, `zsh`, `dash`, or `ksh`, named bare or by path such as `/bin/bash`, with any options before a cluster carrying `c` such as `bash -lc` or `bash -ce`, an `-o`/`-O` option's value included, as in `bash -o pipefail -c`). So an `rm` that is the first word of such a script is matched (`bash -c "rm -rf /"`, `eval 'rm -rf ~/x'`), while an `rm` opening any other quoted string is data, so searching for the command (`grep -rn 'rm -rf /' .`, `grep -c 'rm -rf /' file`) is not itself guarded. They shall also exempt `git rm`, whose deletions this rule set leaves to `watch-git`, which declines them as recoverable staging.

  - **`watch-git`** — destructive git operations. **Block** rules shall cover: `git push --force` (excluding `--force-with-lease`), `git checkout .`, `git restore .`, `git clean -f`, `git stash drop`, `git stash clear`, `git reflog expire/delete`, `git gc --prune=now` (or `=all`) and `git prune` other than a dry run, and `git filter-branch`/`git filter-repo` other than their `--help`, `--version`, `--dry-run`, and `--analyze` forms. **Ask** rules shall cover: `git reset --hard`, `git checkout -- <file>`, `git commit`, `git stash` (except the read-only `git stash list` and `git stash show`), `git push`, `git push --force-with-lease`, `git push --delete` (remote-branch delete, via `--delete`/`-d`/the `:branch` colon refspec), and `git branch -D`. The split follows the no-recovery/recoverable line: deleting a remote branch leaves no remote reflog to recover from, yet you can re-push from a local copy, so it asks rather than blocks; `git branch -D` and `--force-with-lease` are likewise recoverable (local reflog, stale-ref protection) and so ask. Stage-only operations (`git add`, `git rm`, `git rm --cached`, `git reset` without `--hard`) are intentionally unwatched — staging is recoverable, and prompting on it is noise. git accepts any unique prefix of a long option, so a rule naming one shall match each prefix git takes for it (`git reset --h`, `git clean --f`, `git push --del`); force-deleting a branch shall match `-D` and also delete and force given separately, short or long (`-d -f`, `-df`, `--delete --force`). Each rule shall match through git's pre-subcommand global flags (`-C <path>`, `-c <key>=<value>`, `--git-dir[=]<path>`, `-P`), including quoted values containing spaces, so that invocations like `git -C /repo push --force` are not silently bypassed. A subcommand carrying no arguments shall match on whatever follows it in the shell, not only on whitespace or end-of-string, so `(git push)`, `git commit;echo done` and `` `git stash` `` are matched — while a longer subcommand that merely starts with the same word (`git commit-tree`) is not, and neither is a quoted string that merely ends with one, so searching for a guarded command (`grep -rn 'git push' .`) is not itself guarded.

  - **`watch-host`** — actions on the machine as a whole. **Block** rules shall cover: `shutdown`, `reboot`, `halt`, and `poweroff` run as a command (on the same terms as `watch-kill`), `systemctl poweroff`/`reboot`/`halt`/`kexec` (other than `shutdown -c`, which cancels one, and `--help`/`--dry-run` forms), `crontab -r` (which deletes the whole crontab with no backup), and fork bombs (a function that calls itself twice in the background).

  - **`watch-installs`** — package and dependency installation. **Block** rules shall cover: `curl … | sh`, `wget … | sh`, `npm install -g` / `--global`, `brew install` / `upgrade` / `uninstall` (and its `remove` and `rm` aliases) / `reinstall`, `choco install` / `upgrade` / `uninstall`, and `apt install` / `apt-get install`. **Ask** rules shall cover: `npm install`, `yarn add`, `pnpm add`, `pip[3] install`, `cargo add`, `cargo install`, `go install`, `go get`, `gem install`, `composer require`, and `npx` remote-fetch forms (`-y`/`--yes`, `-p`/`--package`, or a versioned/scoped spec such as `pkg@version` or `@scope/pkg`). A bare `npx <tool>` that runs an already-installed binary is allowed, since it executes local code no differently from `npm run`; only the forms that download and run a remote package prompt. An argument-less install shall match on whatever follows it in the shell, so `(npm install)` and `npm install;echo done` are matched on the same terms as `npm install` alone.

  - **`watch-node`** — Node/JavaScript destructive primitives both inline (in `node -e`/`bun -e`/`deno`/`tsx`/`ts-node` bash invocations) and in `.js`/`.mjs`/`.cjs`/`.ts`/`.mts`/`.cts` file content authored via `Write`/`Edit`. **Block** rules shall cover: `fs.rmSync`/`rmdirSync`/`rm` of `/`/`~`/`$HOME`, `child_process` exec-family calls invoking `rm -rf /`, and `new Function(...)`. **Ask** rules shall cover: `fs.rm`/`rmSync` with `recursive: true`, `fs.unlink`/`unlinkSync`, `child_process.exec`/`execSync`, `vm.runInThisContext`/`runInNewContext`/`runInContext`, and `eval(...)`.

  - **`watch-kill`** — commands that signal every process matching a name or pattern, rather than one process by id. **Ask** rules shall cover `pkill` and `killall`. Each rule shall match its command only where the shell runs it as a command: at the start of a command (after a separator, an opening group, or a wrapper such as `sudo`, `nohup`, `xargs`, `env`, or `timeout <duration>`), named bare or by path, or as the first word of a `-c` or `eval` script as `watch-files` defines it. A loose pattern takes down unrelated processes (other Claude Code sessions, editors, dev servers), yet the word itself turns up in ordinary searches and messages, so `grep pkill notes.md` and `echo "use pkill carefully"` are not matched.

  - **`watch-publish`** — package registry publication. **Block** rules shall cover `npm`/`pnpm`/`yarn unpublish` and `gem yank`, since a registry won't accept a removed version again, other than their `--help` and `--dry-run` forms. **Ask** rules shall cover `npm`/`pnpm`/`yarn publish`, with an `except` for `--dry-run`.

  - **`watch-pwsh`** — PowerShell destructive primitives both inline (in `pwsh -Command "..."` bash invocations) and in `.ps1`/`.psm1`/`.psd1` file content authored via `Write`/`Edit`. **Block** rules shall cover: `Format-Volume`, `Clear-Disk`, `Restart-Computer`, `Stop-Computer`, and `Invoke-WebRequest` piped to `Invoke-Expression`/`iex`. **Ask** rules shall cover: `Remove-Item -Recurse -Force`, other `Remove-Item` forms, `Stop-Process -Force`, and `Set-Content`/`Out-File` overwriting sensitive paths (`/etc/`, `~/.ssh/`, `~/.aws/`). The two bash-target `Remove-Item` rules shall carry the `unless_condition` `is_under_scratch_root` ([RL-19]), so a delete is exempt only when every path it names sits under a scratch root.

  - **`watch-self`** — ClaudeWatch's own authority. A prompt-injected agent's shortest path past every other rule set is to turn ClaudeWatch off, so **block** rules shall cover each way the agent can loosen it: a shell write, move, or delete under `~/.claude/claudewatch/` (`>`/`>>`, `rm`, `mv`, `cp`, `tee`, `truncate`, `ln`, `install`, `unlink`, `sed -i`, `perl -i`); a `Write` or `Edit` whose path is under that directory ([RL-21]); `overrides.py set … ask`, `set … off`, and `reset`; `unattended.py off`; `claude plugin disable`/`uninstall` naming ClaudeWatch; and a `.json` file whose content disables the plugin (`"ClaudeWatch@…": false`) or every hook (`"disableAllHooks": true`). Tightening stays open to the agent (`overrides.py set … block`, `unattended.py on`), as do reads. The user makes a loosening change themselves, typed with a `!` prefix or in a separate terminal. Commands that reach the files some other way (an interpreter one-liner, a `jq` pipeline into `settings.json`) are not covered.

  - **`watch-su`** — changing the user a command runs as. **Block** rules shall cover `sudo` and `su`, each matched only where the shell runs it as a command, on the same terms as `watch-kill` above. A cached sudo timestamp or a `NOPASSWD` entry lets `sudo` run as root with no password prompt, and an `ask` is not guaranteed to reach a person ([OUT-04]), so neither tier short of block puts anything between the agent and root. Root-level operations other rule sets name (`sudo pip install`) are covered here rather than per tool.

  - **`watch-python`** — Python destructive primitives both inline (in `python3 -c "..."` bash invocations) and in `.py` file content authored via `Write`/`Edit`. **Block** rules shall cover: `shutil.rmtree` of `/`/`~`/`$HOME`, `pickle.loads`, `__import__('os').system`/`popen`, and `subprocess.*shell=True` containing `rm`/`dd of=/dev/`. **Ask** rules shall cover: other `shutil.rmtree`, `os.remove`/`os.unlink`, `os.system`, generic `subprocess.*shell=True`, `eval(`, and `exec(`.

  - **`watch-remote`** — deleting hosted resources wholesale. **Block** rules shall cover `gh repo delete` and `glab repo delete`, `terraform`/`tofu destroy` and `apply -destroy`, `pulumi destroy`/`down`, and `kubectl delete` of a namespace or with `--all`/`--all-namespaces`/`-A`. Plans and previews (`terraform plan -destroy`, `pulumi preview`), help and client- or server-side dry runs (`--help`, `kubectl … --dry-run=client`), and deleting a single named resource are not matched.

  - **`watch-ruby`** — Ruby destructive primitives both inline (in `ruby -e` bash invocations) and in `.rb` file content authored via `Write`/`Edit`. **Block** rules shall cover: `FileUtils.rm_rf`/`rm_r`/`rm_f` of `/`/`~`/`ENV[...]`, `Marshal.load`/`restore`, and `YAML.load(...)` on input. **Ask** rules shall cover: other `FileUtils.rm_rf`, `File.delete`/`unlink`, `Kernel.system`/`exec` with a string literal, backtick exec with interpolation (`#{...}`), `eval(...)`, and `instance_eval`/`class_eval`/`module_eval`.

  - **`watch-secrets`** — credential and secret exfiltration. A *read* is a reader command (`cat`, `tac`, `bat`, `nl`, `od`, `xxd`, `strings`, `rev`, `egrep`, `fgrep`, `less`, `more`, `head`, `tail`) naming the file, or a bare `<` input redirect, which names the file with no command at all; every rule that matches a read shall recognize this same reader set, and shall pair a reader only with a path before the next `|`, `;`, `&`, or newline that sits outside quotes, outside an fd redirect such as `2>&1`, and unescaped by a backslash; a quote opens only after whitespace or `=`, and a path inside quotes is still a path (`cat "$HOME/.ssh/id_rsa"`). A `head` or `tail` earlier in a pipeline or list then does not turn a later command's path into a read, while the quoted alternation in `egrep 'a|b' ~/.aws/credentials` stays part of the read. `grep`, `sed`, `awk`, and interpreter one-liners also read files, and sit outside the set because they appear in so many ordinary commands. **Block** rules shall cover: reading SSH private keys (`… /.ssh/id_*`), reading cloud credentials (`.aws/credentials`, the AWS SSO and CLI caches under `.aws/sso/cache/` and `.aws/cli/cache/`, `.gcp/`, `.azure/`, `.config/gcloud`), and `echo`/`printf`-ing environment variables whose names match `SECRET|TOKEN|PASSWORD|API.?KEY|PRIVATE.?KEY`. **Ask** rules shall cover: reading files whose names suggest secrets, exporting secret-named env vars inline, reading `.env` files, reading `*.pem`/`*.key`/`*.crt`/`*.cert` files, dumping the environment via `env` or `printenv`, and reading dotfiles. The dotfile rule shall carry an `except` for Claude Code's cache directories (`~/.claude/skills/<skill>/cache/` and `~/.claude/plugins/cache/`), which hold skill state and installed plugin sources. The `except` shall apply only when every dotfile path in the command sits under one of those directories and the command carries no `..` segment, `$`, or backtick that could resolve a path elsewhere, so `~/.claude/.credentials.json` and `~/.claude/skills/<skill>/cache/../../settings.json` still ask; it exempts the dotfile rule alone, so a cache file with a secret-like name still asks. A reader name shall be bounded so that a longer word ending in it (`bobcat`, `my-cat`) is not read as that reader, while a quoted or path-qualified one (`bash -c 'cat …'`, `/bin/cat`) still is, and an input redirect is a `<` that opens no heredoc, herestring, or process substitution. Rules that match commands as full shell tokens (e.g. `env`, `printenv`) shall use shell-command boundaries (start/whitespace/`;`/`&&`/`|`/backtick/parens) rather than `\b` word boundaries, so that hyphenated tokens (`my-env`) do not defeat the match.

- **[SH-02]** Each shipped rule set that includes `target: bash` rules shall declare a top-level `filter` regex that short-circuits commands outside the rule set's domain.
- **[SH-03]** Each shipped rule set shall include `ref` URLs pointing to upstream tool documentation, vendor docs, or a CWE/OWASP entry.
- **[SH-04]** Each shipped rule set shall have a corresponding test file `tests/test-watch-<name>.sh` that exercises representative match/no-match cases.

## 12. Implementation Notes (non-normative)

These describe how the current implementation satisfies the spec. They are
*not* requirements — they may change without bumping the spec version.

- The engine is a single Python script at `scripts/watchdog.py` with a minimal
  pure-Python YAML parser (no PyYAML dependency). The parser supports inline
  list syntax (`['.ps1', '.psm1']`) for the top-level `extensions` field.
- The hook command line is
  `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/watchdog.py" "${CLAUDE_PLUGIN_ROOT}/watches"`,
  invoked from two `PreToolUse` matchers: `Bash|Monitor` and `Write|Edit`.
- The ambient-guidance emission ([HK-04]) is a second SessionStart hook,
  `hooks/emit-rules.sh`, which prints a `# Ambient rules from the ClaudeWatch
  plugin` header followed by each `rules/*.md` file to stdout. Claude Code
  adds SessionStart stdout to context on startup, resume, and compaction, so
  the guidance persists across a compaction. This mirrors the `emit-rules.sh`
  pattern in sibling plugins (`beacon`, `anchor`), which also keep their
  ambient markdown under `rules/`. The YAML rule sets the engine evaluates
  live in a separate `watches/` directory ([HK-01]), so the two never collide.
- The rules-skill ID convention strips the `watch-` prefix from the rule set
  name (e.g. `watch-git` → `git-block-01`).
- Decision logging is implemented in `watchdog.py` as a single `_log_event`
  call after the decision is computed; it is on by default and `CLAUDEWATCH_LOG`
  only redirects the path or opts out. The UTC timestamp is the only clock in
  the script, and it is confined to the logging side channel — the decision path
  remains clock-free and deterministic.
- `/ClaudeWatch:learn` reads the log via `scripts/analyze-decisions.py`, a
  separate read-only, stdlib-only tool. The engine remains the only
  decision-making component; the analyzer never evaluates rules.
- The compound-command detection ([OUT-08]) strips quoted spans with a simple
  regex before scanning for shell operators, keeping the `$(` and unescaped
  backticks a double-quoted span carries. It does not parse escaped quotes
  (`\"`) or `$'…'`, so an operator hidden behind such quoting may go undetected.
  This is safe by construction: the escalation only ever tightens an `ask` into
  a `deny`, so a missed compound form degrades to the existing `ask` (the
  pre-escalation behavior), never to something weaker. The `block`/`ask`
  pattern matching itself runs on the full, unstripped command, so quote
  stripping does not affect which rules fire — only whether a matched `ask` is
  escalated.
